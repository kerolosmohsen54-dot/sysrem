# مقارنة معمقة بين المرجع والنظام الحالي

**تاريخ المراجعة:** 2026-10-29  
**المرجع:** `frontend/reference/precision-slate-erp-v43__3_ (1).html`  
**النطاق:** فحص سلوك HTML المرجعي بعد تشغيل سكربتاته، ومسارات ومكونات React، وواجهات Laravel، ومخططات قاعدة البيانات الموجودة في المشروع. لم تُعدّل ملفات التطبيق أو الخادم أو قاعدة البيانات، ولم تُنفذ معاملات كتابة على قاعدة البيانات.

## الخلاصة التنفيذية

الملف المرجعي نموذج واجهة تفاعلي كبير، وليس تطبيقًا متصلًا بقاعدة بيانات أو API. عند تشغيل سكربتاته محليًا ظهر فيه 68 مقطع شاشة، و12 مجموعة تنقل، و56 عنصر تنقل. هذه الأرقام تشمل تبويبات وتفاصيل ونماذج مالية، ولا تعني 68 وظيفة مستقلة مكتملة. الشيفرة المرجعية لا تستخدم `fetch` أو `XMLHttpRequest`؛ وتستخدم `localStorage` كثيرًا لحفظ بيانات تجريبية محلية.

النظام الحالي تطبيق React فعلي مع مسارات محمية وصلاحيات وطلبات API إلى Laravel. توجد في الخادم وحدات مبيعات ومخزون وخزينة وحاويات ومستخدمين وتقارير ومزامنة جوال تحفظ بيانات عبر جداول قاعدة البيانات. لكن بعض وظائف المرجع غير موجودة أو لا تزال معطلة عمدًا، وبعض صفحات النظام تعرض بيانات محدودة لأن واجهة الخادم لا تقدم كل الملخصات التي يعرضها المرجع.

أهم النتائج:

1. **المرجع لا يثبت أن الوظيفة تعمل أو تُحفظ.** أرقام العملاء والفواتير والأرصدة والرسائل فيه بيانات نموذجية محلية.
2. **معظم العمليات الأساسية موجودة في النظام الحالي مع ربط خادمي**: العملاء، الطلبات والفواتير والتحصيل، المنتجات والمخزون، الحاويات والتكاليف، الخزينة والمصروفات، والشركاء.
3. **المالية المحاسبية الكاملة غير مكتملة:** دليل الحسابات والتسويات والقوائم المحاسبية ليست عمليات متاحة للمستخدم، حتى مع وجود بعض جداول محاسبية في مخطط SQL.
4. **المرجع نفسه غير متسق:** عنوان مركز التقارير يعلن 6 مجموعات و28 نموذجًا، لكن DOM النهائي يعرض 5 بطاقات مجموعات فقط. كما أن بعض روابطه تشير إلى شاشات غير موجودة.
5. **توجد مخاطرة UX في إنشاء الفاتورة الحالية:** عند غياب معاينة الخادم، تعرض الواجهة إجماليات محسوبة محليًا من غير وسمها كتقديرات.

## ما فحصته وكيف تُقرأ الحالات

- **موجود ومربوط:** توجد شاشة React ومسار API وخادم يقرأ أو يكتب بيانات قاعدة البيانات في الشيفرة الحالية. هذا لا يعني أن كل حالة نجحت على قاعدة البيانات الحية.
- **جزئي:** توجد شاشة أو عملية، لكن جزءًا من البيانات أو قواعد العمل أو حقول المرجع غير متاح.
- **متوقف عمدًا:** الشاشة توضح أن التنفيذ ينتظر عقدًا أو قرارًا محاسبيًا/تشغيليًا.
- **نموذج محلي:** الواجهة تعرض محتوى محليًا تجريبيًا ولا ترسله إلى الخادم.

قُرئت ملفات migrations ومخطط SQL ومسارات Laravel، لكن لم أتحقق من أن كل migration مطبقة على قاعدة التشغيل الحالية، ولم أنشئ سجلًا أو أجرّب كل عملية كتابة. فحص الاتصال السابق بقاعدة التطبيق لا يساوي قبولًا تشغيليًا لكل وحدة.

## جرد المرجع الفعلي

| البند | ما ظهر بعد تشغيل سكربتات ملف المرجع |
|---|---|
| الحجم | 821,223 بايت تقريبًا، صفحة HTML واحدة كبيرة تضم CSS وJavaScript وبيانات تجريبية. |
| المقاطع | 68 عنصرًا من `section-content`، بينها صفحات، ونوافذ تفاصيل، وأجزاء فرعية للمالية. |
| التنقل | 12 مجموعة نهائية و56 عنصر تنقل تقريبًا، مع عناصر كثيرة أضيفت من سكربتات لاحقة. |
| مركز التقارير | النص يعلن 6 فئات و28 تقريرًا، لكن البطاقات النهائية الظاهرة خمس فقط: المبيعات، الحاويات، الأرباح، المخزون، والمالية. فئة العملاء والموردين المعلنة لا تظهر كبطاقة مستقلة. |
| الاتصال والحفظ | لا يوجد `fetch` أو `XMLHttpRequest`؛ وتظهر `localStorage` 55 مرة في المصدر. هذه إشارات إلى تخزين ومحاكاة محلية، لا إلى حفظ في MySQL. |
| قوائم الشاشات | توجد مقاطع الطلبات والتسليمات، لكن قائمة التنقل النهائية لا تعرض مدخلًا واضحًا لهما. |
| روابط معطوبة محتملة | توجد استدعاءات `showSection` إلى `settings` و`expenses` و`cashiers` بينما لا توجد مقاطع `sec-settings` و`sec-expenses` و`sec-cashiers` في DOM النهائي؛ ودالة التنقل تعرض خطأ عند غياب المقطع. |

المرجع جميل بصريًا ومنظم بصريًا على سطح المكتب: RTL، داكن افتراضيًا، خط عربي، قوائم قابلة للطي، بحث عام، إشعارات، حالات، وجداول مضغوطة. لكنه كثيف جدًا، ويخلط بين صفحات تشغيلية ونماذج محلية وروابط ترويجية. لذلك لا ينبغي نسخ عناصره الوهمية أو اعتبار كل زر دليلًا على عملية مكتملة.

## عناصر في المرجع بلا تنفيذ متصل مكافئ

| وظيفة المرجع | حالة النظام الحالي |
|---|---|
| مرفقات العميل | جدول metadata عام موجود في مخطط SQL، لكن تعليق الجدول يقول إن البايتات وعلاقة المالك غير ممثلة؛ لا API رفع/عرض/تنزيل ولا تدفق في React. |
| نوع تسوية المرتجع: استرداد نقدي/رصيد/استبدال | لا يظهر في نموذج/API المرتجع الحالي كقرار محفوظ. |
| الحجز الفعلي للمخزون عند تأكيد الطلب | تبويب توضيحي، لا حجز تشغيلي. |
| التسليم الجزئي ومسح QR | غير متاح كتدفق مستخدم مكتمل. |
| طباعة ملصقات باركود | الباركود موجود للمنتج والبحث، لكن شاشة الملصقات غير موجودة. |
| ميزانيات المصروفات، التكرار، مقارنة الشهور، توقع السيولة، الأقساط، الأموال المنتظرة | غير متصل؛ تظهر كقائمة وظائف مرجعية غير مرتبطة. لا توجد واجهات API تشغيلية لها. |
| 28 تقريرًا ومؤشرات الرسوم التفصيلية | المرجع يعرض عناوين/نماذج أكثر مما توجد بيانات API وشاشات فعلية في النظام. |

## وظائف في النظام الحالي أعمق أو خارج المرجع

- ربط تطبيق الهاتف بالخادم: مصادقة جهاز، مزامنة، التقاط ورسائل مالية، قنوات دفع ومصادر وفئات، وأرشفة/استعادة الرسائل.
- تطبيق خادمي دائم للمشتريات وفواتير الشراء ودفعات الشركاء، وهي مفاهيم لها نماذج/لوحات أيضًا في إضافات المرجع. الفرق أن النظام يربطها بمسارات حفظ وصلاحيات وحركات خزينة واعتماد، بينما المرجع يعرضها كواجهة محلية.
- تقرير خادمي لمصالحة توزيع أرباح الشركة والشركاء والحاويات؛ المرجع يعرض معلومات أرباح الشركاء، لكن ليس كتقرير مصالحة موحد موثوق من الخادم.
- اعتماد الجرد الدوري وحد المخزون لكل موقع، وتاريخ تكلفة المنتج، وإيصالات الحاوية القابلة للعكس، وسجل تغيّر الحالات.
- صلاحيات خادمية وسجل تدقيق وجلسة حقيقية بدل كلمات المرور التجريبية المحلية في ملف المرجع.

هذه الزيادة لا تعني أن كل صفحة إضافية مكتملة في الواجهة: على سبيل المثال، صفحة المخزون التالف ومساراته معتمدة جزئيًا/متوقفة في React؛ لذلك تُعامل كميزة موجودة جزئيًا وليست تدفقًا جاهزًا للمستخدم.

## ملاحظات UX مرتبة حسب الأثر

### عالية الأثر

1. إجماليات الفاتورة في `InvoiceFormPage` تستخدم `invoiceTotalEstimate` و`subtotal` المحسوبين في المتصفح عندما لا تصل معاينة الخادم. تظهر الأرقام ضمن الإجمالي والمتبقي والتحصيل دون تسمية «تقديري». وعند التحصيل الفوري تُجهز مبالغ الدفع من المعاينة الحالية أو التقدير قبل preflight؛ بعده تتحقق الواجهة من التحذيرات فقط ولا تستخدم `grand_total_egp` الذي عاد لتحديث/إعادة فحص مبالغ الدفع. هذا قد ينتج فرقًا عن إجمالي الخادم، خصوصًا مع الضريبة والتقريب. يجب أن تكون نتيجة preflight الحديثة هي المصدر الوحيد للتحقق من المبلغ وتكوين الدفع، أو إيقاف الإرسال عند غيابها.
2. مرتجع مجاني موجود له مكوّن منفصل لكنه غير موصول في المسار الرئيسي؛ يجب توحيد نقطة إنشاء المرتجع وربطها بالحقول المدعومة فعلًا.
3. المالية تجمع وظائف كثيرة في مرجع واحد، بينما النظام الحالي يوزعها على صفحات. إعادة التنظيم الحالية أوضح، لكن يحتاج المستخدم ملخصًا واضحًا لما هو متصل فعلًا وما هو محاسبي متوقف، لا أن تبدو بطاقات الانتظار كوظائف جاهزة.

### متوسطة الأثر

4. المستخدم لا يرى في صفحة الطلبات أن التأكيد لا يحجز رصيدًا؛ يجب أن يكون الفرق بين «تأكيد الطلب» و«حجز المخزون» صريحًا.
5. في شاشة إنشاء الحاوية ينبغي توضيح أن اختيار المنتجات يسجل **محتويات الشحنة**، وأن الكمية لا تصبح مخزونًا متاحًا إلا بعد الاستلام. هذا يعالج الالتباس بين إضافة حاوية وإضافة منتج للمخزون.
6. «تحميل PDF» في صفحة الطباعة اسم أوسع مما تنفذه العملية؛ الحالي هو نافذة طباعة المتصفح، ومن المستخدم يختار PDF يدويًا. المشاركة تختصر بيانات الفاتورة ولا ترسل مستندًا مباشرًا إلى واتساب.
7. تغيير الدور عبر نص رموز مفصولة بفواصل أصعب من اختيار دور واضح أو عرض صلاحياته؛ الخادم نفسه يحتفظ بمصفوفة صلاحيات الأدوار.

### التصميم العام والجوال

- اتجاه RTL والخط العربي والمكونات المشتركة متوفرة في React، والقائمة الجانبية تتكيف مع الهاتف.
- الجداول العامة تتحول إلى بطاقات في المقاسات الضيقة؛ وهذا أوضح من التمرير الأفقي. بعض جداول الفواتير/المرتجعات لا تزال تتبع قواعد تنسيق خاصة.
- توجد في React مزايا بحث لوحة المفاتيح والإجراءات السريعة وقابلية التنقل بالصلاحيات وحالات التحميل والخطأ والفراغ، وهي أفضل من الاعتماد على التنبيهات والبيانات الوهمية في نموذج المرجع.
- تقرير المقارنة الصوري الموجود داخل `frontend/parity-report/REPORT.md` تاريخي بتاريخ 2026-10-11، ويسجل اختلافات كبيرة في لوحة التحكم والطباعة وبعض التقارير. تغيّر تنظيم المالية بعد ذلك، لذلك لا يُعد ذلك التقرير قياسًا نهائيًا للنسخة الحالية. يجب إعادة الالتقاط قبل ادعاء التطابق البصري.

## أولويات إغلاق الفجوات

1. إزالة أو وسم كل إجمالي فاتورة يحسبه المتصفح؛ التأكيد لا يتم دون نتيجة معاينة خادم حديثة.
2. توحيد المرتجع في شاشة واحدة: مرتبط/حر، سبب وحالة، وطريقة المعالجة المعتمدة، مع عدم إظهار خيار لا يحفظه API.
3. إظهار حجز المخزون بوضوح كغير متاح، وعدم إعطاء تبويب الحجز مظهرًا تشغيليًا.
4. فصل المالية إلى «يعمل الآن» و«ينتظر اعتمادًا محاسبيًا»، مع إبقاء المسارات المتوقفة معلنة بوضوح.
5. تحديد ما إذا كانت التقارير تحتاج اعتمادًا محاسبيًا، ثم إضافة مخطط API محدد قبل بناء رسوم أو مؤشرات إضافية.
6. إما إتاحة مرفقات العملاء والاستيراد من الويب بعقد محفوظ، أو إزالة الادعاء بأنهما وظيفتان مكتملتان.
7. إكمال ملف المستخدم الشخصي/إدارة الأدوار وإعدادات النسخ الاحتياطي فقط بعد تحديد صلاحياتها ومسار الخادم.
8. إعادة التقاط ومراجعة الواجهات عند 1440 و768 و390 بكسل بعد آخر تغييرات React، ثم اختبار حالات النماذج لا الصفحات الفارغة فقط.
