# تقرير رحلة الاستلام من الحاوية

التاريخ: 17 أكتوبر 2026
الفرع المحلي: `container-intake-from-start-20261017`

## ما كان موجودًا

- شاشة الحاويات كانت تنشئ بيانات الحاوية الأساسية فقط.
- شاشة تفاصيل الحاوية تضيف منتجًا مباشرة إلى قاعدة البيانات قبل إضافة بند الحاوية، مع خطوة استلام منفصلة.
- إنشاء المنتجات والمخازن من شاشتيهما كان متاحًا بالفعل.
- لم توجد شاشة حاويات داخل تطبيق الهاتف.

## ما أُضيف

- نموذج استلام متكامل من شاشة الحاويات: اسم ورقم فريد وجهة القدوم، بنود لمنتجات موجودة أو منتجات جديدة مؤقتة، الكمية وسعر الشراء، المصروفات وتوزيعها، مخزن الاستلام، ومعاينة التكلفة قبل الحفظ.
- نافذة منتج سريع تحفظ بيانات المنتج مؤقتًا في النموذج. لا يُرسل المنتج الجديد إلى واجهة المنتجات قبل طلب الحفظ المتكامل. الاسم والكود المكرران يتحقق منهما النموذج والخادم، مع اقتراح اختيار المنتج الموجود.
- نافذة مخزن سريع تحفظ المخزن فورًا ككيان مستقل، وتختاره تلقائيًا. عند عدم وجود مخزن تظهر «لا يوجد مخزن»، ويظل حفظ الحاوية معطلًا حتى اختيار مخزن.
- واجهة API جديدة تنشئ المنتجات الجديدة والحاوية والبنود والتكاليف والاستلام وحركات المخزون والتدقيق ومفتاح منع التكرار داخل transaction واحدة. يستخدم الاستلام مسار الاستلام الموجود ويضيف رقم الحاوية إلى مرجع الحركة.
- عرض اسم الحاوية في القوائم والتفاصيل، وإظهار رابط مصدر المنتج الجديد إلى الحاوية. بقيت شاشتا المنتجات والمخازن ومساراتهما القائمة كما هي.
- زر الحفظ يتعطل أثناء الطلب، ويعيد الخادم نتيجة الطلب السابق عند وصول إعادة بنفس مفتاح منع التكرار.

## التحقق

- قاعدة `.env` المستخدمة: `erp_scratch` على `127.0.0.1:3306`، MySQL 8.4.3. طُبقت migration الإضافية عليها؛ لم يتغير هيكل الجداول القائمة بطريقة مدمرة.
- تحقق تكاملي داخل transaction خارج المستودع في `D:\acceptance-run\container-intake-verify-codex-20261017.php`: 3 منتجات جديدة ومنتج موجود، مخزن سريع، 8 قطع، قيمة شراء 150.00 ج.م، مصروفات 60.00 ج.م، إجمالي تكلفة 210.00 ج.م ومتوسط 26.25 ج.م/قطعة. تحقق الاختبار من تكلفة كل صنف، رصيد المخزن، حركة مرجعها رقم الحاوية، رابط مصدر المنتج، ومستحقات الحاوية.
- إعادة الطلب بالمفتاح نفسه أعادت الحاوية والإيصال نفسيهما؛ لم تنشئ حاوية أو إيصالًا ثانيًا.
- أُحدث فشل متعمد بعد إنشاء الحاوية والمنتج والبند الأول، عند تكرار كود منتج في البند التالي. أُعيدت كل الكتابات بفضل transaction. اختُبرت الكميات صفر وسالب وكسرية ونصية وفارغة، واسم منتج مكرر، وسعر شراء نصي، وحقل مطلوب فارغ؛ رُفضت جميعها قبل الحفظ. اختُبر أيضًا غياب نوع المصروف وأعاد رسالة عربية.
- بعد rollback عادت أعداد جداول البيانات التي لمسها السيناريو إلى خط الأساس صفرًا: الحاويات، المنتجات، المواقع، حركات المخزون وبنودها، بنود وتكاليف الحاوية، الإيصالات، مفاتيح منع التكرار، وسجل التدقيق.
- اختبار واجهة الحاويات: 11 اختبارًا ناجحًا، ومنها إنشاء المخزن من النافذة، إبقاء المنتج مؤقتًا حتى حفظ الحاوية، اقتراح اختيار منتج موجود عند تكرار الاسم، وإلغاء النموذج دون إنشاء منتج.
- فحوصات `npm run lint` و`npm run typecheck` و`npm run build` نجحت. مجموعة الواجهة الكاملة نجحت: 44 ملف اختبار و192 اختبارًا. ظهر في اختبارات أخرى تحذير MSW لطلب صندوق الرسائل غير المعالج وتحذير React Query لبيانات رصيد غير معرفة؛ لم يفشل أي اختبار.
- لم تُشغّل مجموعة PHPUnit كاملة؛ أُجري تحقق تكاملي مخصص على قاعدة الاختبار داخل transaction مع rollback، وفُحصت صياغة PHP والمسارات وحالة migration.

## حدود التغطية

- لا توجد شاشة حاويات في تطبيق الهاتف، لذلك لم يُضف مسار هاتف خاص بالحاويات.
- فحص الحفظ المتكامل نُفذ على API داخل transaction تُلغى في النهاية، واختبار الواجهة استخدم محاكاة API؛ لم تُجرَ جلسة قبول مرئية في Chrome.
- إضافة المخزن تحفظه مباشرة كما هو مطلوب؛ إذا أُلغي نموذج الحاوية بعد إنشاء المخزن، يظل المخزن موجودًا. المنتجات الجديدة لا تحفظ عند الإلغاء.
